# Rumelt 任务方案输出契约

本契约规定方案文档的固定结构与可验证语义。方案必须先诊断关键挑战，再选择指导方针，最后设计连贯行动；不能把用户目标换一种说法后直接列待办。

## 文档外壳

每份方案必须以且只以以下三个 frontmatter 字段开头：

```yaml
---
plan_schema: rumelt-task-plan/v1
status: DRAFT
mode: full
---
```

- `plan_schema` 必须为 `rumelt-task-plan/v1`。
- `status` 只能为 `DRAFT`、`READY_FOR_REVIEW` 或 `APPROVED`。
- `mode` 只能为 `full`、`compact` 或 `diagnostic-exploration`。
- frontmatter 后使用一个 `# 任务方案：<标题>`，再按固定顺序使用八个二级标题；不得改名、合并或跳过。章节中确实不适用的字段写 `不适用：<原因>`，不得留空。

固定二级标题如下：

```markdown
## 任务事实与边界
## 关键挑战诊断
## 指导方针
## 近端目标与杠杆点
## 连贯行动
## 链式弱环节与风险
## 假设与失败信号
## 决策与批准
```

## 模式

### `full`

用于开放、复杂、多阶段、高返工成本、有显著不确定性或权限风险的任务。完整展开八章，不得用“同上”等省略关键因果关系。

### `compact`

仅用于输入输出明确、低风险、易撤销、依赖少的任务。仍须保留 frontmatter、八章和完整行动字段，但每章可压缩为一至三行，行动通常为一至三项。若存在外部写入、不可逆动作、敏感数据、关键未知项或冲突要求，不得使用此模式。

### `diagnostic-exploration`

用于现有证据不足以可靠确定关键挑战的任务。不得伪造主要诊断，也不得规划最终任务的实质执行；本轮指导方针只能用于获取证据、比较竞争性诊断并形成选择条件。

- 在“关键挑战诊断”写 `主要诊断：未确立`，不要为未知诊断创建虚假的 `D-*`。
- 至少列出两个 `ALT-*` 竞争性诊断、各自证据需求与证伪条件。
- 行动的 `addresses` 主要引用 `U-*` 或 `ALT-*`。
- 近端目标必须减少明确的 `U-*`，并规定何时退出探索模式。
- 探索方案本身无硬错误时可以是 `READY_FOR_REVIEW`；探索结束后，必须另建 `full` 或 `compact` 方案，才能执行最终任务。

## 字段与 ID

ID 在一份方案内唯一、连续且不可复用。使用两位数字，从 `01` 开始。文本发生实质变化时保留 ID 并记录变化；删除后不要把该 ID 指给别的对象。

| 前缀 | 语义 | 必需性 |
| --- | --- | --- |
| `REQ-*` | 用户明确要求或成功条件，不包含 Agent 推测 | 必需 |
| `F-*` | 已核实事实，须说明证据或来源 | 有事实时必需 |
| `C-*` | 权限、时间、范围、格式、安全等约束 | 必需 |
| `U-*` | 会影响诊断或执行的未知项 | 有未知时必需 |
| `ASM-*` | 为继续规划暂时采用、可被推翻的假设 | 有假设时必需 |
| `D-*` | 对关键挑战的主要诊断；`full`/`compact` 恰有一个 | 条件必需 |
| `ALT-*` | 与主要诊断结构不同的竞争性诊断 | 不确定时必需 |
| `G-*` | 指导方针：总体应对方法与取舍规则 | 必需 |
| `NG-*` | 主动不做项，说明被排除的路线 | 必需 |
| `O-*` | 当前阶段可达、可验收的近端目标 | 必需 |
| `L-*` | 可能放大结果的杠杆点及资源集中方式 | `full` 必需 |
| `A-*` | 可执行、可验收的行动 | 必需 |
| `W-*` | 可能使整体失效的弱环节或风险 | 有链式依赖时必需 |
| `H-*` | 关于方法为何有效的可检验假设 | 必需 |
| `Q-*` | 必须由用户决定或补充的信息 | 有待决事项时必需 |

`F-*`、`ASM-*`、`U-*` 必须分开；“可能”“大概”“通常”不能把假设变成事实。每个 ID 后必须写有信息量的陈述，不得只写“质量问题”“做好文章”等空标签。

## 八个必需章节

### 任务事实与边界

按以下字段书写：

```markdown
- 表面任务：<用户要求完成什么>
- 用户明确要求：
  - REQ-01 | <要求或成功条件>
- 已核实事实：
  - F-01 | <事实> | 依据：<来源或观察>
- 约束：
  - C-01 | <约束>
- 未知项：
  - U-01 | <未知项> | 影响：<它会改变什么判断>
- 暂定假设：
  - ASM-01 | <假设> | 验证方式：<如何推翻或确认>
- 可用输入、工具与权限：<清单>
```

没有事实、未知或假设时分别写 `无：<原因>`，不要编造条目。

### 关键挑战诊断

`full` 与 `compact` 使用：

```markdown
- 主要诊断：D-01 | <阻碍成功的关键原因，不是期望结果>
- 支持链：F-01, C-01 -> D-01
- 为何关键：<它如何支配其他问题或结果>
- 竞争性诊断：ALT-01 | <不同因果解释> | 当前为何不选：<证据>
- 证伪条件：<什么观察会推翻 D-01>
```

`diagnostic-exploration` 使用：

```markdown
- 主要诊断：未确立
- 竞争性诊断：
  - ALT-01 | <候选解释> | 所需证据：<证据> | 证伪条件：<条件>
  - ALT-02 | <候选解释> | 所需证据：<证据> | 证伪条件：<条件>
- 当前不能选择的原因：U-01
- 退出探索的判定规则：<如何选择、否决或继续保留候选>
```

### 指导方针

至少包含：

```markdown
- G-01 | <总体应对方法；说明优先优化什么以及如何取舍>
- 优先级：<冲突时谁优先>
- 自主范围：<AI 可自行决定什么>
- 询问条件：<何时必须暂停并询问用户>
- 主动不做：
  - NG-01 | <被排除的路线> | 原因：<为何不服务当前挑战>
```

指导方针必须排除至少一条看似可行的路线；“专业、深入、全面”等愿望不能单独充当 `G-*`。

### 近端目标与杠杆点

```markdown
- O-01 | <本轮可达且可验收的状态> | 减少未知：U-01 或 无
- 可行性：<现有输入、能力和权限为何足够>
- L-01 | <关键支点> | 集中资源：<注意力、时间、工具或检查如何集中>
- 杠杆失效信号：<什么结果说明 L-01 判断错误>
- 暂不追求的终局：<本轮不承诺什么>
```

`compact` 模式若杠杆概念不产生实际区分，可写 `不适用：任务只有一个直接、低风险转换步骤`。

### 连贯行动

必须使用以下精确列名：

| ID | 行动 | addresses | implements | input | output | dependencies | permissions | acceptance |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| A-01 | <动词开头的动作> | D-01 | G-01, O-01 | <具体输入或 ID> | <可交给下一步检查/使用的产物> | none | <所需权限及当前是否具备> | <可观察的通过条件> |

规则：

- 每个行动都必须填写九列；不得留空、写“视情况”“尽量”或只写形容词。
- `addresses` 只能引用已定义的 `D-*`、`U-*`、`W-*` 或 `ALT-*`；不得只引用用户目标。
- `implements` 只能引用已定义的 `G-*`、`O-*`；至少各引用一个。
- `input` 引用具体资料、ID 或上游 `A-*` 的输出。
- `output` 是明确产物或可观察状态，不能等同于动作本身。
- `dependencies` 只写前置 `A-*`；无依赖写 `none`。不得循环依赖。
- `permissions` 写明读、写、联网、外部发送、审批等需要及当前状态。
- `acceptance` 必须可由人、工具或后续行动观察；“质量高”“用户满意”不够。

### 链式弱环节与风险

```markdown
- W-01 | <最弱环节或风险> | 影响：<为何会使整体失效>
- 进入闸门：A-02 仅在 <A-01 的可观察门槛> 后开始
- 串行步骤：<A-* 及原因>
- 可并行步骤：<A-* 及原因；没有则写无>
- 中止条件：<触发后停止什么>
- 恢复或返工：<从 D/G/A 哪一层重新检查>
```

不要把所有任务强行描述为链式系统。没有链式弱环节时写明为何多个输出可以独立贡献或择优，并仍列一般风险。

### 假设与失败信号

至少写一个完整检验单元：

```markdown
- H-01 | 假设：<为什么所选方法会奏效>
  - 预期观察：<可观察变化>
  - 最小验证：<低成本检验>
  - 通过标准：<阈值或判定规则>
  - 失败信号：<反例或负面结果>
  - 失败后重查：D-01 / G-01 / A-01 / 输入或权限条件
```

失败信号必须允许当前方案被修正，不能把任何结果都解释为方案正确。

### 决策与批准

```markdown
- 当前状态：DRAFT
- 状态理由：<为何处于该状态>
- 可自主执行：<仅指获批后无需再次询问的范围>
- 必须由用户决定：Q-01 | <选择或补充信息；没有则写无>
- 缺少的权限或资料：<没有则写无>
- 未解决的硬错误：<没有则写无>
- 保留警告：<没有则写无；否则写警告与接受理由>
- 批准范围：<尚未批准 / 用户明确批准的 A-* 与边界>
- 下一步：<等待批准、补充诊断证据或按批准范围执行>
```

## 可追溯与依赖规则

合格方案至少形成以下闭环：

```text
REQ/F/C/U/ASM -> D 或 ALT -> G/NG -> O/L -> A -> acceptance/H -> 回查 D、G 或 A
```

- 每个 `D-*` 必须被事实、约束或已标明的不确定性支持。
- 每个 `G-*` 必须回应主要 `D-*`；探索模式则回应 `ALT-*` 的区分需要。
- 每个 `O-*` 必须推进 `G-*`，并产生本轮可验收状态。
- 每个 `A-*` 必须同时有 `addresses` 与 `implements`；孤立动作删除、降级或拆到另一方案。
- 每个行动输出若被后续使用，后续行动的 `input` 和 `dependencies` 必须引用它。
- 每个关键 `U-*` 必须由某个行动减少，或成为阻止方案进入执行的 `Q-*`。
- 每个 `W-*` 必须有闸门、中止条件或返工动作，不能只登记风险。
- 引用不存在的 ID、同一 ID 表示多个对象或行动循环依赖均为错误。

## 状态与执行闸门

### `DRAFT`

用于初稿、存在待决选择、缺少关键资料/权限、含硬错误或尚未完成语义审查的方案。可以输出和讨论，不得据此执行任务。

### `READY_FOR_REVIEW`

表示结构验证通过、无硬错误、关键未知已处理或被明确设为审批问题，方案在现有权限下原则上可执行。它仍然不是执行授权；输出后停止并等待用户审阅。

### `APPROVED`

只有用户能够把当前版本设为 `APPROVED`。AI 不得根据沉默、原始任务中的一般性“请完成”或自己判断低风险来推定批准。用户须在看到当前方案后明确批准全部方案或具体 `A-*`。

- 用户只批准部分行动时，`批准范围` 必须列出具体 `A-*`；其余行动保持禁止。
- 方案内容在批准后发生任何实质变化，立即退回 `DRAFT` 或 `READY_FOR_REVIEW` 并重新批准。
- 批准不扩大原有工具、数据、目录、对外发送或破坏性操作权限。
- 规划所需的只读检查与方案验证不算最终任务执行；任何会改变任务对象或外部状态的动作都受批准闸门约束。
- `compact` 模式同样遵守计划/执行分离，不因低风险自动执行。

## 硬错误

出现任一项时，状态不得为 `READY_FOR_REVIEW` 或 `APPROVED`：

1. frontmatter 缺失、值非法，或八个必需章节缺失、改名、乱序。
2. `full`/`compact` 没有且仅有一个主要 `D-*`，或把目标、愿景、待办冒充诊断。
3. `diagnostic-exploration` 伪造主要诊断、少于两个竞争性诊断，或包含最终任务的实质执行行动。
4. 没有明确 `G-*`、取舍或至少一个 `NG-*`。
5. 行动表缺列、单元格为空、引用不存在的 ID、存在循环依赖，或行动未同时填写 `addresses` 与 `implements`。
6. 行动缺少具体输入、输出、权限或可观察验收条件。
7. 关键未知没有验证行动或 `Q-*`，弱环节没有闸门、中止或返工规则。
8. 所需权限不具备却宣称可执行，或计划行动超出用户授权与资料边界。
9. 未获得用户对当前版本的明确批准却标记 `APPROVED` 或开始执行。
10. 使用 `compact` 隐藏显著风险、冲突要求、敏感数据、不可逆动作或关键未知。
11. 事实、假设与未知混写，导致诊断依据不可复核。
12. 验收条件与用户要求无关，或没有失败信号使方案可以被现实推翻。

## 警告

警告不自动阻止 `READY_FOR_REVIEW`，但必须在“决策与批准”中记录、修正或说明接受理由；若影响安全、授权或基本可行性，则升级为硬错误。

- 使用“专业、深入、全面、最佳”等词，却没有可观察定义。
- 存在多个主要挑战，未说明为何聚焦其中一个。
- 行动过多、都标为高优先级，或多项行动解决同一问题却没有增量价值。
- `full` 模式没有可信杠杆点，或资源没有真正集中。
- 为显示完整而制造无意义串行步骤，或忽略明显的关键依赖。
- 验收只依赖同一个 AI 的主观自评，没有外部证据、工具检查或人工判断。
- 失败后只写“重试”，没有指出回查诊断、方针、行动、输入还是权限。
- 主动不做项只是重复范围边界，没有体现真正取舍。
